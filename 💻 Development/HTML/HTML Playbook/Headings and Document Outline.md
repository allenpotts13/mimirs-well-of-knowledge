# <span class="rune">ᛟ</span> Headings and Document Outline

> *Headings aren't font-size shortcuts — they're a table of contents baked directly into the page that screen reader users navigate by, and search engines read as your content's structure.*

---

## 🎯 Purpose

A sighted user can scan a page visually — bold text, size jumps, whitespace — and instantly grasp its structure without reading a word. A screen reader user can't do that by default; they either listen to the entire page top to bottom, or they navigate by structure. Headings (`<h1>`–`<h6>`) are that structure. This concept exists because the heading hierarchy is one of the very few places where HTML markup *is* the navigation system, not just a hint for one.

---

## 🧠 Key Ideas

- Convention: use **one logical `<h1>` per page**, representing the page's main topic — think of it as the page's title, distinct from `<title>` in `<head>` (which is for the browser tab/bookmarks, not the visible page).
- Heading levels should **nest logically**, like an outline: `<h2>` for major sections, `<h3>` for subsections within an `<h2>`, and so on — you shouldn't jump from `<h2>` straight to `<h4>`.
- **Never skip or choose heading levels for their default font size** — `<h3>` is not "a smaller heading," it's "a subsection three levels deep." Font size is CSS's job, always.
- Screen reader users routinely pull up a **list of all headings on a page** (a standard feature in every major screen reader) as a primary way to skim and jump directly to the section they want — exactly like a sighted user skimming a table of contents.
- The sequence of headings on a page forms the **document outline** — a structural summary that both assistive technology and search engines rely on to understand the page's shape.

---

## ⚙️ How It Works

Picture a screen reader user landing on a long article page. They don't want to listen to the whole thing read aloud just to find the "Shipping & Returns" section. Instead, they press a single key (commonly `H` in most screen readers) to jump heading-to-heading, or open a headings list — essentially an auto-generated table of contents — and jump straight there. This only works if the page's headings are marked up as actual `<h1>`–`<h6>` elements *in a sensible order*. If "Shipping & Returns" is styled to look bold and large using a `<div class="fake-heading">`, it's invisible to that navigation entirely — it doesn't exist as a heading to the accessibility tree, no matter how it looks.

The nesting matters too. A well-formed outline reads like a table of contents:

```
h1: Company Blog
  h2: How We Built Our New Warehouse
    h3: Site Selection
    h3: Construction Timeline
  h2: Meet the Team
    h3: Engineering
    h3: Operations
```

Skipping from `<h2>` to `<h4>` to get a smaller default font breaks that outline — a screen reader user hearing "heading level 4" right after "heading level 2" will reasonably assume there's a missing level 3 section, or be confused about how deeply nested the content actually is.

---

## 💻 Examples

```html
<!-- Correct: one h1, logical nesting -->
<h1>Web Development Foundations</h1>

<h2>HTML Basics</h2>
<h3>Elements and Tags</h3>
<h3>Attributes</h3>

<h2>CSS Basics</h2>
<h3>Selectors</h3>
<h3>The Box Model</h3>
```

```html
<!-- WRONG: heading level chosen for font size, not structure -->
<h2>Section Title</h2>
<h4>A minor note I wanted smaller text for</h4>
<!-- This isn't a subsection of anything — it's just misuse of h4 as a font-size utility class -->

<!-- RIGHT: use the correct level, then style with CSS -->
<h2>Section Title</h2>
<h3 class="minor-note">A minor note, styled smaller with CSS</h3>
```

```html
<!-- WRONG: a "heading" that isn't actually one -->
<div class="heading-style">Our Services</div>
<!-- Invisible to heading navigation, document outline, and screen readers entirely -->

<!-- RIGHT -->
<h2>Our Services</h2>
```

## 🚀 Real World Applications

- Screen reader users on long-form content (news articles, documentation, recipe blogs) routinely use the headings list to skip straight past a wall of introductory text to the actual content.
- Search engines use heading structure as a strong signal for what a page is about and how its content is organized, influencing both ranking and how "featured snippets" get extracted.
- Table-of-contents plugins and "reading time" tools (common on blogs and documentation sites) are auto-generated by walking the heading structure — a broken outline produces a broken table of contents.
- Browser "reader mode" features rely on heading hierarchy to build a clean, distraction-free version of a page.
- Accessibility auditing tools (axe, WAVE, Lighthouse) specifically flag skipped heading levels and missing/multiple `<h1>` elements as issues.

---

## ⚖️ Advantages

- A correct heading structure gives you free navigation, free SEO signal, and a free content outline, all from markup you'd be writing anyway.
- Keeping headings semantic and using CSS for size means changing a section's visual weight never requires touching its markup or meaning.
- A clean outline makes the page easier for *every* developer maintaining it to understand at a glance, not just users of assistive tech.

---

## ⚠️ Limitations

- HTML doesn't enforce heading order — nothing stops you from writing `<h1>` then `<h4>`; it's a convention you have to maintain by discipline (or lint tooling), not something the browser blocks.
- "One `<h1>` per page" is a strong convention, not a hard technical rule — the HTML spec historically allowed multiple `<h1>`s within sectioning elements, but sticking to one keeps the outline unambiguous and matches what most tooling and screen readers expect.
- Deeply nested content can genuinely run out of heading levels (`<h6>` is the last one) — at that depth, it's usually a sign the content needs restructuring, not more heading levels.

---

## 🚨 Common Mistakes

- Choosing a heading level based on what font size it defaults to, instead of what depth it represents in the outline — then "fixing" the size with inline styles rather than fixing the *level* and using CSS.
- Using multiple `<h1>` tags scattered through a page without a clear reason, muddying the outline.
- Skipping levels (`<h2>` to `<h4>`) purely because an `<h3>` looked "too big" or "too small" for a given spot.
- Using bold or large `<p>` or `<div>` text to visually fake a heading instead of using a real heading element.
- Forgetting a `<h1>` entirely on a page, leaving no clear top-level topic for screen readers or search engines to latch onto.

## 💡 Wisdom from Mímir

If I'm ever tempted to change a heading tag just to get a different font size, that's my signal to stop and open the CSS file instead. I think of the heading levels as a contract with a reader I can't see — the moment I break that contract for a purely visual reason, I've made the page lie to someone navigating by ear.
