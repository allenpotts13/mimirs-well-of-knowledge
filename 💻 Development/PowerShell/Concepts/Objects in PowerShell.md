# <span class="rune">ᛟ</span> Objects in PowerShell

> *Every other shell passes text between commands. PowerShell passes whole objects — and that single difference is why everything else about it feels different.*

---

## 🎯 Purpose

Bash, cmd, and every classic Unix shell move plain text between commands — one program prints a string, the next has to parse it back apart. PowerShell instead passes fully structured **.NET objects**, complete with named properties and methods, from one command straight into the next.

This concept exists because almost every "why does PowerShell do it that way" question traces back to this one design decision. Understanding objects first makes the pipeline, filtering, and formatting all click into place — trying to learn those before this is like learning `GROUP BY` before understanding rows.

---

## 🧠 Key Ideas

- A command like `Get-Process` doesn't print text — it returns a collection of `System.Diagnostics.Process` **objects**, each with real properties (`Name`, `Id`, `CPU`, `WorkingSet`) and methods (`.Kill()`).
- What you *see* on screen is a formatted **display** of those objects, generated by PowerShell's formatting system — it is not what actually gets passed to the next command.
- `Get-Member` is the single most important discovery tool in PowerShell — pipe anything into it to see every property and method the object actually has.
- Properties are accessed with dot notation (`$proc.Name`), exactly like in any .NET language, because they *are* .NET objects.
- Because objects carry real types, PowerShell knows a `DateTime` is a date and an `Int32` is a number — no manual parsing required to sort, compare, or do math on command output.

---

## ⚙️ How It Works

When you run `Get-Process`, PowerShell doesn't ask the operating system for a block of text. It calls into .NET, gets back a collection of live `Process` objects, and hands that collection to whatever's next in the pipeline — unchanged, with every property still intact.

Only at the very end of the pipeline, when there's nothing left to receive the objects, does PowerShell's formatting subsystem step in and decide how to *display* them as text in the console. That's why `Get-Process | Select-Object Name` shows a table — the table is a rendering choice made at output time, not the object's real shape.

```text
Get-Process → [Process objects with all their properties] → Select-Object Name → [objects, now with ONLY the Name property] → console formatter → text table
```

---

## 💻 Examples

```powershell
# See what an object actually IS, not what it looks like on screen
Get-Process | Get-Member

# Access a property directly with dot notation
(Get-Process -Name explorer).Id

# Prove it's a real object, not text: sort numerically without any parsing
Get-Process | Sort-Object CPU -Descending | Select-Object -First 5

# Prove it's a real DateTime, not a string
(Get-Item C:\Windows).CreationTime.AddDays(30)
```

---

## 🚀 Real World Applications

- Piping `Get-Process` straight into `Sort-Object`/`Where-Object` by CPU or memory, with zero text parsing
- Exporting live objects directly to CSV or JSON (`Export-Csv`, `ConvertTo-Json`) and getting correctly typed columns automatically
- Calling `.Kill()`, `.Stop()`, or other methods directly on returned objects instead of shelling out to a separate command
- Comparing two objects' properties directly (`Compare-Object`) instead of diffing raw text output

---

## ⚖️ Advantages

- No fragile text-parsing (`awk`, regex, column-splitting) needed to extract data from command output.
- Type safety carries through the whole pipeline — dates stay dates, numbers stay numbers.
- Discoverability: `Get-Member` tells you exactly what's available on anything, without reading documentation first.
- The same object model works identically whether the data came from a file, the registry, WMI, or a REST API.

---

## ⚠️ Limitations

- Object-based output doesn't play naturally with tools expecting plain text (need `ConvertTo-Json`, `Out-String`, or similar to bridge to non-PowerShell consumers).
- Slightly steeper learning curve for anyone coming from a text-stream shell background — the instinct to `grep`/`awk` has to be replaced with `Where-Object`/`Select-Object`.
- Some cmdlets return different object types depending on parameters used, which can surprise scripts that assume a fixed shape.

---

## 🚨 Common Mistakes

- Trying to string-parse `Get-Process` or similar output instead of just selecting the property you need — a holdover habit from other shells.
- Assuming what's printed to the console *is* the object — it's a formatted view; piping into another cmdlet still gives you the full original object.
- Forgetting to check `Get-Member` before writing filtering logic, then guessing at property names incorrectly.
- Comparing object properties with `-eq` when the property is actually a collection (e.g., comparing an array property to a single string will silently behave unexpectedly).
